HƯỚNG DẪN CHI TIẾT 2.8 - 2.9
============================

Tài liệu này được viết theo dạng tutorial để bạn có thể vừa đưa vào báo cáo, vừa dùng làm checklist triển khai thực tế.


## 2.8. PHÁT TRIỂN DỰ ÁN VỚI SPRING BOOT

### 2.8.1 Thiết kế Database cho ứng dụng

Mục tiêu:
- Xây dựng mô hình dữ liệu nhất quán với nghiệp vụ quản lý tài liệu.
- Bảo đảm dữ liệu an toàn, dễ mở rộng, và dễ truy vấn.

A. Xác định thực thể cốt lõi
- User: lưu thông tin tài khoản và vai trò.
- Folder: tổ chức tài liệu theo thư mục.
- Document: lưu metadata tài liệu.
- Permission: lưu quyền truy cập tài liệu theo người dùng.
- SharingRequest: lưu yêu cầu xin quyền truy cập.

B. Thiết kế quan hệ
- User 1 - N Document (owner_id).
- User 1 - N Folder (owner_id).
- Folder 1 - N Document (folder_id).
- Document 1 - N Permission.
- User 1 - N Permission (recipient_id).
- Document 1 - N SharingRequest.

C. Chuẩn hóa cột dữ liệu chính
- User:
  user_id, name, email, password, role, created_at.
- Folder:
  folder_id, name, owner_id, created_at.
- Document:
  doc_id, title, owner_id, metadata, created_at, updated_at, folder_id, file_data, original_filename, content_type.
- Permission:
  perm_id, doc_id, user_id, access_type.
- SharingRequest:
  request_id, doc_id, requester_id, status, requested_at, permission.

C1. Chi tiết data type đề xuất (PostgreSQL)

Schema dưới đây đã được đối chiếu theo dữ liệu thực tế từ lệnh \d trong psql.

- Bảng User
  - user_id: INTEGER, PRIMARY KEY, DEFAULT nextval('users_user_id_seq').
  - name: VARCHAR(100), NOT NULL.
  - email: VARCHAR(255), NOT NULL, UNIQUE.
  - password: VARCHAR(255), NOT NULL.
  - role: VARCHAR(20), NOT NULL, CHECK role IN ('User', 'Admin').
  - created_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.

- Bảng Folder
  - folder_id: INTEGER, PRIMARY KEY, DEFAULT nextval('folders_folder_id_seq').
  - name: VARCHAR(255), NOT NULL.
  - owner_id: INTEGER, NULL, FOREIGN KEY -> users(user_id) ON DELETE CASCADE.
  - created_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.

- Bảng Document
  - doc_id: INTEGER, PRIMARY KEY, DEFAULT nextval('documents_doc_id_seq').
  - title: VARCHAR(255), NOT NULL.
  - owner_id: INTEGER, NULL, FOREIGN KEY -> users(user_id) ON DELETE CASCADE.
  - metadata: JSONB, NULL.
  - created_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.
  - updated_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.
  - folder_id: INTEGER, NULL, FOREIGN KEY -> folders(folder_id) ON DELETE SET NULL.
  - file_data: BYTEA, NULL.
  - original_filename: VARCHAR(255), NULL.
  - content_type: VARCHAR(255), NULL.

- Bảng Permission
  - perm_id: INTEGER, PRIMARY KEY, DEFAULT nextval('permissions_perm_id_seq').
  - doc_id: INTEGER, NULL, FOREIGN KEY -> documents(doc_id) ON DELETE CASCADE.
  - user_id: INTEGER, NULL, FOREIGN KEY -> users(user_id) ON DELETE CASCADE.
  - access_type: VARCHAR(20), NOT NULL, CHECK access_type IN ('Owner', 'Editor', 'Viewer').

- Bảng SharingRequest
  - request_id: INTEGER, PRIMARY KEY, DEFAULT nextval('sharing_requests_request_id_seq').
  - doc_id: INTEGER, NULL, FOREIGN KEY -> documents(doc_id) ON DELETE CASCADE.
  - requester_id: INTEGER, NULL, FOREIGN KEY -> users(user_id) ON DELETE CASCADE.
  - status: VARCHAR(20), DEFAULT 'Pending', CHECK status IN ('Pending', 'Approved', 'Rejected').
  - requested_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.
  - permission: VARCHAR(20), NOT NULL.

D. Ràng buộc cần có
- Unique(email) cho User.
- Check access_type cho Permission (Owner, Editor, Viewer).
- Check/status enum cho SharingRequest (Pending, Approved, Rejected).
- Foreign key đầy đủ và index cho cột truy vấn thường xuyên:
  owner_id, folder_id, doc_id, user_id, requester_id, status.

D1. Các điểm còn thiếu hoặc nên cải thiện trong schema hiện tại
- Chưa có UNIQUE(doc_id, user_id) trong bảng permissions, có thể gây trùng quyền cho cùng một user trên cùng một tài liệu.
- Các cột owner_id, doc_id, user_id, requester_id đang cho phép NULL; nếu nghiệp vụ không cho phép bản ghi mồ côi, nên thêm NOT NULL.
- Bảng users hiện không có updated_at; nếu cần audit thay đổi hồ sơ người dùng, nên bổ sung cột này.
- Bảng sharing_requests chưa thể hiện rõ người nhận yêu cầu (target_user_id); nếu luồng chia sẻ cần người nhận cụ thể, nên bổ sung cột target_user_id.

E. Hướng triển khai với Spring Boot
- Dùng JPA Entity cho từng bảng.
- Dùng migration tool (Flyway hoặc Liquibase) để version hóa schema.
- Không sửa schema thủ công trực tiếp trên production.

F. Đoạn viết mẫu cho báo cáo
"Cơ sở dữ liệu được thiết kế theo mô hình quan hệ, xoay quanh các thực thể User, Folder, Document, Permission và SharingRequest. Mô hình này bảo đảm khả năng quản lý tài liệu theo chủ sở hữu, kiểm soát truy cập theo mức quyền, và xử lý luồng chia sẻ qua cơ chế yêu cầu duyệt. Các ràng buộc khóa ngoại, unique key và chỉ mục truy vấn được áp dụng để tăng tính toàn vẹn và hiệu năng hệ thống."


### 2.8.2 Xây dựng chức năng CRUD

Mục tiêu:
- Triển khai đầy đủ Create, Read, Update, Delete cho module chính.

A. Chiến lược triển khai theo tầng
- Controller: nhận request/response.
- Service: xử lý nghiệp vụ.
- Repository: truy cập dữ liệu.
- DTO/Mapper: tách biệt dữ liệu API và dữ liệu persistence.

B. CRUD theo module

1) Folder CRUD
- Create: tạo thư mục mới theo owner hiện tại.
- Read: lấy danh sách thư mục theo owner.
- Update: đổi tên thư mục.
- Delete: xóa thư mục (kiểm tra ràng buộc tài liệu con).

2) Document CRUD
- Create: upload tài liệu, lưu file storage + metadata DB.
- Read: danh sách tài liệu theo quyền truy cập.
- Update: đổi tên, đổi thư mục, cập nhật metadata.
- Delete: xóa metadata và file vật lý (nếu dùng S3/local storage).

3) SharingRequest CRUD (theo nghiệp vụ)
- Create: gửi yêu cầu chia sẻ.
- Read: xem danh sách yêu cầu gửi/nhận.
- Update: duyệt/từ chối yêu cầu.
- Delete: thường không xóa cứng, nên dùng cập nhật trạng thái.

C. Quy tắc nghiệp vụ quan trọng
- Người dùng chỉ sửa/xóa tài liệu khi có quyền phù hợp.
- Tất cả API nhạy cảm phải xác thực JWT.
- Kiểm tra quyền trước khi trả dữ liệu chi tiết tài liệu.

D. Xử lý lỗi chuẩn
- 400: dữ liệu đầu vào không hợp lệ.
- 401: thiếu token hoặc token sai.
- 403: không đủ quyền.
- 404: không tìm thấy tài nguyên.
- 409: xung đột dữ liệu (ví dụ unique key).

E. Đoạn viết mẫu cho báo cáo
"Các chức năng CRUD được triển khai theo kiến trúc nhiều tầng (Controller - Service - Repository) nhằm tách biệt trách nhiệm và tăng khả năng bảo trì. Mỗi thao tác đều được kiểm soát bởi điều kiện xác thực và phân quyền, giúp bảo đảm tính an toàn khi xử lý dữ liệu tài liệu và luồng chia sẻ trong hệ thống."


### 2.8.3 Tạo và quản lý API Endpoints

Mục tiêu:
- Chuẩn hóa API REST, dễ tích hợp frontend và dễ kiểm thử.

A. Nguyên tắc đặt endpoint
- Dùng version: /api/v1/...
- Dùng danh từ số nhiều: /users, /documents, /folders
- Method đúng chuẩn:
  GET đọc, POST tạo, PATCH cập nhật một phần, DELETE xóa.

B. Nhóm endpoint điển hình

1) Authentication
- POST /api/v1/auth/register
- POST /api/v1/auth/login
- GET /api/v1/auth/me
- POST /api/v1/auth/logout

2) Folder
- GET /api/v1/folders
- POST /api/v1/folders
- PATCH /api/v1/folders/:id
- DELETE /api/v1/folders/:id

3) Document
- POST /api/v1/documents/upload
- GET /api/v1/documents
- GET /api/v1/documents/:id
- PATCH /api/v1/documents/:id
- POST /api/v1/documents/:id/move
- DELETE /api/v1/documents/:id

4) Permission và Sharing
- GET /api/v1/permissions
- POST /api/v1/sharing-requests
- GET /api/v1/sharing-requests
- POST /api/v1/sharing-requests/:id/approve
- POST /api/v1/sharing-requests/:id/reject

5) Admin
- GET /api/v1/users
- PATCH /api/v1/users/:id/role
- GET /api/v1/users/audit/export

C. Chuẩn response API
- Hệ thống nên dùng một cấu trúc phản hồi thống nhất cho tất cả endpoint để frontend dễ xử lý và dễ kiểm thử.
- Response thành công thường có các trường:
  - code: mã trạng thái hoặc mã nghiệp vụ.
  - message: thông báo ngắn gọn cho người dùng.
  - data: dữ liệu trả về của request.
  - timestamp: thời điểm phản hồi.
- Response thất bại thường có các trường:
  - code: mã lỗi.
  - message: mô tả lỗi ngắn gọn.
  - error_details: thông tin chi tiết để debug.
  - timestamp: thời điểm lỗi xảy ra.
  - path: đường dẫn endpoint bị lỗi.
- Ví dụ response thành công:
  {
    "code": 200,
    "message": "Success",
    "data": {...},
    "timestamp": "2026-08-14T10:30:00"
  }
- Ví dụ response thất bại:
  {
    "code": 403,
    "message": "Forbidden",
    "error_details": "User does not have permission to update this document.",
    "timestamp": "2026-08-14T10:30:00",
    "path": "/api/v1/documents/12"
  }

D. Tài liệu hóa API
- Dùng Swagger/OpenAPI để:
  - mô tả request body,
  - response schema,
  - auth requirement,
  - ví dụ gọi API.

E. Đoạn viết mẫu cho báo cáo
"Hệ thống API được tổ chức theo chuẩn RESTful với tiền tố phiên bản /api/v1. Endpoints được phân nhóm theo module nghiệp vụ (Authentication, Folder, Document, Sharing, Admin), kết hợp chuẩn phản hồi thống nhất và tài liệu hóa qua OpenAPI nhằm hỗ trợ tích hợp và kiểm thử hiệu quả."


### 2.8.4 Kiểm thử API bằng Postman

Mục tiêu:
- Xác minh endpoint hoạt động đúng về nghiệp vụ, bảo mật và xử lý lỗi.

A. Chuẩn bị môi trường Postman
- Tạo Environment: local, staging, production.
- Biến môi trường cơ bản:
  base_url, access_token_user_a, access_token_user_b, access_token_admin, test_user_id, test_folder_id, test_document_id, test_request_id.

A1. Quy ước test chung
- Header chuẩn cho API bảo vệ:
  Authorization: Bearer {{access_token_user_a}} (hoặc user_b/admin).
- Content-Type:
  - application/json cho request JSON.
  - multipart/form-data cho upload tài liệu.
- Thứ tự chạy khuyến nghị: Auth -> Folder -> Document -> Sharing/Permission -> Admin.
- Mỗi request đều kiểm tra tối thiểu:
  - Status code.
  - Cấu trúc response (code, message, data hoặc error_details).
  - Giá trị nghiệp vụ quan trọng trong data.

A2. Dữ liệu test đề xuất
- User A (role User): người sở hữu tài liệu.
- User B (role User): người nhận chia sẻ.
- Admin (role Admin): kiểm thử endpoint quản trị.
- 01 file mẫu để upload (PDF hoặc DOCX).

B. Quy trình test khuyến nghị

B1. Nhóm Authentication

1) POST /api/v1/auth/register
- Mục đích: đăng ký tài khoản mới.
- Body mẫu:
  {
    "name": "Test User A",
    "email": "usera_test@example.com",
    "password": "Abc@123456"
  }
- Kỳ vọng:
  - 200/201 khi đăng ký thành công.
  - 409 khi email đã tồn tại.
  - 400 khi thiếu trường bắt buộc.

2) POST /api/v1/auth/login
- Mục đích: đăng nhập lấy JWT.
- Body mẫu:
  {
    "email": "usera_test@example.com",
    "password": "Abc@123456"
  }
- Kỳ vọng:
  - 200 khi thành công.
  - Response chứa token.
  - Lưu token vào biến {{access_token_user_a}} bằng script Postman.
  - 401 khi sai mật khẩu.

3) GET /api/v1/auth/me
- Mục đích: xác minh token hợp lệ.
- Header: Authorization: Bearer {{access_token_user_a}}.
- Kỳ vọng:
  - 200 và trả về đúng email/role của user đăng nhập.
  - 401 khi thiếu hoặc sai token.

4) POST /api/v1/auth/logout
- Mục đích: kết thúc phiên đăng nhập.
- Kỳ vọng:
  - 200 khi logout thành công.
  - 401 nếu token không hợp lệ.

B2. Nhóm Folder

1) POST /api/v1/folders
- Mục đích: tạo thư mục mới.
- Body mẫu:
  {
    "name": "Folder API Test"
  }
- Kỳ vọng:
  - 200/201 khi tạo thành công.
  - Lưu folder_id vào {{test_folder_id}}.
  - 400 khi name rỗng.

2) GET /api/v1/folders
- Mục đích: lấy danh sách thư mục của user.
- Kỳ vọng:
  - 200 và có thư mục vừa tạo.
  - Không trả thư mục của user khác nếu không có quyền.

3) PATCH /api/v1/folders/:id
- Mục đích: đổi tên thư mục.
- Kỳ vọng:
  - 200 khi đổi tên thành công.
  - 404 khi folder_id không tồn tại.
  - 403 khi user không sở hữu thư mục.

4) DELETE /api/v1/folders/:id
- Mục đích: xóa thư mục.
- Kỳ vọng:
  - 200/204 khi xóa thành công.
  - 404 nếu không tồn tại.
  - 403 nếu không có quyền.

B3. Nhóm Document

1) POST /api/v1/documents/upload
- Mục đích: upload tài liệu mới.
- Form-data mẫu:
  - file: chọn tệp mẫu.
  - title: "Tai lieu test API".
  - folder_id: {{test_folder_id}} (nếu có).
- Kỳ vọng:
  - 200/201 khi upload thành công.
  - Response trả doc_id, lưu vào {{test_document_id}}.
  - 400 khi thiếu file.

2) GET /api/v1/documents
- Mục đích: lấy danh sách tài liệu.
- Kỳ vọng:
  - 200 và có tài liệu vừa upload.
  - Hỗ trợ lọc/phân trang nếu API có.

3) GET /api/v1/documents/:id
- Mục đích: xem chi tiết tài liệu.
- Kỳ vọng:
  - 200 khi có quyền truy cập.
  - 403 khi user không có quyền.
  - 404 khi doc_id không tồn tại.

4) PATCH /api/v1/documents/:id
- Mục đích: cập nhật metadata hoặc title.
- Body mẫu:
  {
    "title": "Tai lieu test API - updated",
    "metadata": {
      "category": "report",
      "tag": ["api", "postman"]
    }
  }
- Kỳ vọng:
  - 200 khi cập nhật thành công.
  - 403 nếu không đủ quyền (Viewer không được sửa).

5) POST /api/v1/documents/:id/move
- Mục đích: di chuyển tài liệu sang thư mục khác.
- Body mẫu:
  {
    "folder_id": 123
  }
- Kỳ vọng:
  - 200 khi move thành công.
  - 404 khi folder đích không tồn tại.
  - 403 nếu không đủ quyền.

6) DELETE /api/v1/documents/:id
- Mục đích: xóa tài liệu.
- Kỳ vọng:
  - 200/204 khi xóa thành công.
  - 403 khi không có quyền xóa.
  - 404 khi tài liệu không tồn tại.

B4. Nhóm Permission và Sharing

1) GET /api/v1/permissions
- Mục đích: kiểm tra danh sách quyền đã cấp.
- Kỳ vọng:
  - 200 và có bản ghi quyền liên quan tới {{test_document_id}} sau khi approve request.

2) POST /api/v1/sharing-requests
- Mục đích: User A gửi yêu cầu chia sẻ.
- Body mẫu (điều chỉnh theo payload thật của backend):
  {
    "doc_id": {{test_document_id}},
    "permission": "Viewer"
  }
- Kỳ vọng:
  - 200/201 khi tạo request thành công.
  - Lưu request_id vào {{test_request_id}}.
  - 400 khi thiếu trường bắt buộc.

3) GET /api/v1/sharing-requests
- Mục đích: xem danh sách yêu cầu chia sẻ.
- Kỳ vọng:
  - 200.
  - User A thấy request đã gửi; user xử lý thấy request liên quan theo nghiệp vụ hệ thống.

4) POST /api/v1/sharing-requests/:id/approve
- Mục đích: duyệt yêu cầu chia sẻ.
- Kỳ vọng:
  - 200 khi duyệt thành công.
  - Status request chuyển sang Approved.
  - Kiểm tra tiếp GET /api/v1/permissions thấy quyền mới được cấp.

5) POST /api/v1/sharing-requests/:id/reject
- Mục đích: từ chối yêu cầu chia sẻ.
- Kỳ vọng:
  - 200 khi từ chối thành công.
  - Status request chuyển sang Rejected.
  - Không phát sinh quyền mới trong permissions.

B5. Nhóm Admin

1) GET /api/v1/users
- Mục đích: lấy danh sách người dùng (chỉ Admin).
- Kỳ vọng:
  - 200 với token admin.
  - 403 với token user thường.

2) PATCH /api/v1/users/:id/role
- Mục đích: cập nhật vai trò người dùng.
- Body mẫu:
  {
    "role": "Admin"
  }
- Kỳ vọng:
  - 200 khi admin cập nhật thành công.
  - 400 khi role không hợp lệ.
  - 403 khi user thường gọi endpoint này.

3) GET /api/v1/users/audit/export
- Mục đích: xuất log/audit.
- Kỳ vọng:
  - 200 với admin.
  - Content-Type phù hợp (JSON/CSV/file theo thiết kế).
  - 403 với user thường.

B6. Ma trận kiểm thử lỗi bắt buộc (negative tests)
- 401 Unauthorized:
  - Gọi endpoint bảo vệ mà không gửi Authorization header.
  - Gửi token sai định dạng hoặc token hết hạn.
- 403 Forbidden:
  - User B cố sửa/xóa tài liệu của User A khi chưa được cấp quyền.
  - User thường gọi endpoint Admin.
- 404 Not Found:
  - Dùng id không tồn tại cho folder/document/request.
- 409 Conflict:
  - Đăng ký email đã tồn tại.
- 400 Bad Request:
  - Thiếu field bắt buộc hoặc sai kiểu dữ liệu request body.

C. Viết test script trong Postman
- Kiểm tra status code bằng pm.response.to.have.status(...).
- Kiểm tra field bắt buộc trong JSON response:
  - pm.expect(json).to.have.property('code');
  - pm.expect(json).to.have.property('message');
- Lưu biến cho request sau:
  - postman.setEnvironmentVariable('access_token_user_a', json.data.token);
  - postman.setEnvironmentVariable('test_document_id', json.data.doc_id);
- Với flow cần đổi user, tách rõ 3 collection/folder test:
  - User A Flow.
  - User B Flow.
  - Admin Flow.

D. Báo cáo kết quả test
- Bảng tổng hợp:
  endpoint, method, test case, expected status, actual status, pass/fail, ghi chú lỗi.
- Tỷ lệ pass khuyến nghị cần theo dõi:
  - Smoke test: 100% pass.
  - Regression test: >= 95% pass trước khi demo/release.

E. Đoạn viết mẫu cho báo cáo
"Kiểm thử API được thực hiện bằng Postman theo chuỗi nghiệp vụ hoàn chỉnh từ xác thực, quản lý thư mục/tài liệu đến chia sẻ và phân quyền. Kết quả kiểm thử xác nhận các endpoint chính hoạt động đúng chức năng, đồng thời bảo đảm các kiểm tra bảo mật và xử lý lỗi theo thiết kế."

4. Cấu hình static website hosting (hoặc dùng CloudFront).
5. Cấu hình policy/public access đúng cách.
6. Cập nhật biến môi trường frontend trỏ về API backend thật.

Checklist S3:
- Frontend truy cập được ổn định.
- Gọi API backend đúng domain triển khai.
- Không còn hard-code localhost trong bản build production.

## 2.8. PHÁT TRIỂN DỰ ÁN VỚI SPRING BOOT

Trong giai đoạn phát triển backend, nhóm sử dụng Spring Boot để hiện thực toàn bộ nghiệp vụ quản lý tài liệu, từ xác thực người dùng, quản lý thư mục, quản lý tài liệu đến chia sẻ và phân quyền. Kiến trúc hệ thống được tổ chức theo mô hình nhiều tầng nhằm tách biệt rõ trách nhiệm giữa tầng điều khiển, tầng xử lý nghiệp vụ và tầng truy cập dữ liệu.


### 2.8.1 Thiết kế Database cho ứng dụng

Cơ sở dữ liệu của hệ thống được thiết kế theo mô hình quan hệ nhằm bảo đảm tính nhất quán dữ liệu và hỗ trợ tốt cho các thao tác truy vấn, cập nhật và kiểm soát quyền truy cập. Các thực thể chính bao gồm User, Folder, Document, Permission và SharingRequest.

Thực thể User lưu thông tin tài khoản người dùng như họ tên, email, mật khẩu đã mã hóa và vai trò hệ thống. Thực thể Folder dùng để tổ chức tài liệu theo cấu trúc thư mục và liên kết với người sở hữu. Thực thể Document lưu metadata của tài liệu như tên, loại tệp, kích thước, đường dẫn lưu trữ, chủ sở hữu và thư mục chứa tài liệu. Thực thể Permission lưu quyền truy cập mà một người dùng được cấp đối với một tài liệu cụ thể. Thực thể SharingRequest lưu các yêu cầu chia sẻ tài liệu và trạng thái xử lý của từng yêu cầu.

Đối chiếu schema PostgreSQL thực tế cho thấy hệ thống hiện dùng các cột sau: users(user_id, name, email, password, role, created_at), folders(folder_id, name, owner_id, created_at), documents(doc_id, title, owner_id, metadata, created_at, updated_at, folder_id, file_data, original_filename, content_type), permissions(perm_id, doc_id, user_id, access_type), sharing_requests(request_id, doc_id, requester_id, status, requested_at, permission).

Các quan hệ trong hệ thống được xác định như sau:
- Một User có thể sở hữu nhiều Folder và nhiều Document.
- Một Folder có thể chứa nhiều Document.
- Một Document có thể được gán nhiều Permission.
- Một Document có thể phát sinh nhiều SharingRequest.
- Một User có thể là người gửi hoặc người nhận yêu cầu chia sẻ.

Chi tiết kiểu dữ liệu đề xuất cho từng bảng (PostgreSQL) như sau:

- Bảng User
  - user_id: INTEGER, PRIMARY KEY, DEFAULT nextval('users_user_id_seq').
  - name: VARCHAR(100), NOT NULL.
  - email: VARCHAR(150), NOT NULL, UNIQUE.
  - password: VARCHAR(255), NOT NULL.
  - role: VARCHAR(20), NOT NULL, CHECK role IN ('User', 'Admin').
  - created_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.

- Bảng Folder
  - folder_id: INTEGER, PRIMARY KEY, DEFAULT nextval('folders_folder_id_seq').
  - name: VARCHAR(100), NOT NULL.
  - owner_id: INTEGER, NULL, FOREIGN KEY -> users(user_id) ON DELETE CASCADE.
  - created_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.

- Bảng Document
  - doc_id: INTEGER, PRIMARY KEY, DEFAULT nextval('documents_doc_id_seq').
  - title: VARCHAR(255), NOT NULL.
  - owner_id: INTEGER, NULL, FOREIGN KEY -> users(user_id) ON DELETE CASCADE.
  - metadata: JSONB, NULL.
  - created_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.
  - updated_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.
  - folder_id: INTEGER, NULL, FOREIGN KEY -> folders(folder_id) ON DELETE SET NULL.
  - file_data: BYTEA, NULL.
  - original_filename: VARCHAR(255), NULL.
  - content_type: VARCHAR(255), NULL.

- Bảng Permission
  - perm_id: INTEGER, PRIMARY KEY, DEFAULT nextval('permissions_perm_id_seq').
  - doc_id: INTEGER, NULL, FOREIGN KEY -> documents(doc_id) ON DELETE CASCADE.
  - user_id: INTEGER, NULL, FOREIGN KEY -> users(user_id) ON DELETE CASCADE.
  - access_type: VARCHAR(20), NOT NULL, CHECK access_type IN ('Owner', 'Editor', 'Viewer').

- Bảng SharingRequest
  - request_id: INTEGER, PRIMARY KEY, DEFAULT nextval('sharing_requests_request_id_seq').
  - doc_id: INTEGER, NULL, FOREIGN KEY -> documents(doc_id) ON DELETE CASCADE.
  - requester_id: INTEGER, NULL, FOREIGN KEY -> users(user_id) ON DELETE CASCADE.
  - status: VARCHAR(20), DEFAULT 'Pending', CHECK status IN ('Pending', 'Approved', 'Rejected').
  - requested_at: TIMESTAMP WITHOUT TIME ZONE, DEFAULT CURRENT_TIMESTAMP.
  - permission: VARCHAR(20), NOT NULL.

Ghi chú đối chiếu thực tế:
- Schema hiện tại chưa có cột target_user_id trong sharing_requests.
- Schema hiện tại chưa có UNIQUE(doc_id, user_id) trong permissions.

Để tăng tính toàn vẹn dữ liệu, hệ thống áp dụng các ràng buộc như unique cho email người dùng, unique cho cặp document_id - recipient_id trong Permission, cùng với các khóa ngoại giữa Document, Folder và User. Ngoài ra, các trường truy vấn thường xuyên như owner_id, folder_id, document_id, recipient_id và status được lập chỉ mục để tối ưu hiệu năng.

Triển khai thực tế được thực hiện bằng JPA Entity kết hợp với migration tool để version hóa schema. Cách làm này giúp quá trình phát triển và triển khai dễ kiểm soát hơn, đồng thời hạn chế sai lệch giữa mã nguồn và cấu trúc dữ liệu thực tế.


### 2.8.2 Xây dựng chức năng CRUD

Các chức năng CRUD của hệ thống được triển khai theo kiến trúc phân tầng gồm Controller, Service và Repository. Cách tổ chức này giúp tách biệt rõ việc tiếp nhận request, xử lý nghiệp vụ và tương tác với cơ sở dữ liệu.

Ở module thư mục, hệ thống hỗ trợ tạo mới thư mục, lấy danh sách thư mục, cập nhật tên thư mục và xóa thư mục. Các thao tác này luôn gắn với người dùng hiện tại để bảo đảm chỉ chủ sở hữu hoặc tài khoản hợp lệ mới có thể thay đổi dữ liệu.

Ở module tài liệu, hệ thống hỗ trợ upload tài liệu, xem danh sách tài liệu, xem chi tiết tài liệu, cập nhật metadata, di chuyển tài liệu sang thư mục khác và xóa tài liệu. Khi upload, file được lưu vào kho lưu trữ, còn metadata được ghi vào cơ sở dữ liệu. Khi xóa, hệ thống cần xử lý đồng thời phần dữ liệu trong database và phần file vật lý nếu có.

Ở module chia sẻ, CRUD được hiểu theo nghiệp vụ gồm tạo yêu cầu chia sẻ, xem danh sách yêu cầu, duyệt yêu cầu, từ chối yêu cầu và cập nhật trạng thái xử lý. Các yêu cầu chia sẻ thường không xóa cứng mà được quản lý bằng trạng thái để dễ truy vết lịch sử.

Tất cả các thao tác CRUD đều được kiểm tra quyền trước khi thực thi. Người dùng chỉ có thể sửa hoặc xóa tài liệu khi có quyền phù hợp, còn các thao tác quản trị chỉ dành cho tài khoản có vai trò Admin. Khi có lỗi đầu vào hoặc xung đột dữ liệu, hệ thống trả về mã lỗi phù hợp như 400, 401, 403, 404 hoặc 409 để frontend xử lý thống nhất.


### 2.8.3 Tạo và quản lý API Endpoints

API của hệ thống được thiết kế theo chuẩn RESTful và có version hóa thông qua tiền tố /api/v1 để thuận tiện cho việc mở rộng trong tương lai. Các endpoint được tổ chức theo từng nhóm nghiệp vụ để dễ quản lý và dễ tích hợp với frontend.

Nhóm Authentication bao gồm các endpoint:
- POST /api/v1/auth/register: đăng ký tài khoản mới.
- POST /api/v1/auth/login: đăng nhập và nhận JWT.
- GET /api/v1/auth/me: lấy thông tin người dùng hiện tại.
- POST /api/v1/auth/logout: đăng xuất và kết thúc phiên làm việc.

Nhóm Folder bao gồm các endpoint:
- GET /api/v1/folders: xem danh sách thư mục.
- POST /api/v1/folders: tạo thư mục mới.
- PATCH /api/v1/folders/:id: cập nhật thông tin thư mục.
- DELETE /api/v1/folders/:id: xóa thư mục.

Nhóm Document bao gồm các endpoint:
- GET /api/v1/documents: xem danh sách tài liệu.
- POST /api/v1/documents/upload: tải tài liệu lên hệ thống.
- GET /api/v1/documents/:id: xem chi tiết tài liệu.
- PATCH /api/v1/documents/:id: cập nhật tài liệu.
- POST /api/v1/documents/:id/move: di chuyển tài liệu sang thư mục khác.
- DELETE /api/v1/documents/:id: xóa tài liệu.

Nhóm Permission và Sharing bao gồm các endpoint:
- GET /api/v1/permissions: xem quyền truy cập.
- POST /api/v1/sharing-requests: gửi yêu cầu chia sẻ.
- GET /api/v1/sharing-requests: xem danh sách yêu cầu chia sẻ.
- POST /api/v1/sharing-requests/:id/approve: duyệt yêu cầu.
- POST /api/v1/sharing-requests/:id/reject: từ chối yêu cầu.

Nhóm Admin bao gồm các endpoint:
- GET /api/v1/users: xem danh sách người dùng.
- PATCH /api/v1/users/:id/role: thay đổi vai trò người dùng.
- GET /api/v1/users/audit/export: xuất nhật ký quản trị.

Tất cả API phản hồi theo một cấu trúc thống nhất, bao gồm mã trạng thái, thông báo và dữ liệu trả về. Các endpoint bảo vệ đều yêu cầu token JWT trong header Authorization, và backend kiểm tra quyền trước khi trả dữ liệu hoặc cho phép thay đổi dữ liệu.


### 2.8.4 Kiểm thử API bằng Postman

Kiểm thử API được thực hiện bằng Postman theo hướng end-to-end, bao phủ toàn bộ nhóm endpoint Authentication, Folder, Document, Permission/Sharing và Admin. Mỗi test case đều kiểm tra đồng thời ba lớp: tính đúng nghiệp vụ, tính đúng phân quyền và tính đúng cấu trúc response.

Nhóm tạo 3 token riêng cho User A, User B và Admin để mô phỏng đúng luồng nghiệp vụ thật. Các biến môi trường bắt buộc gồm base_url, access_token_user_a, access_token_user_b, access_token_admin, test_folder_id, test_document_id và test_request_id. Thứ tự chạy test được chuẩn hóa theo chuỗi: Auth -> Folder -> Document -> Sharing/Permission -> Admin -> Negative tests.

Với Authentication, nhóm kiểm thử register, login, me và logout; trọng tâm là xác minh token hợp lệ, phát hiện sai mật khẩu, và bắt lỗi trùng email. Với Folder và Document, nhóm kiểm thử đầy đủ CRUD, bao gồm tạo dữ liệu mới, đọc danh sách, cập nhật thông tin, di chuyển tài liệu và xóa dữ liệu; đồng thời xác nhận lỗi 403 khi user không có quyền chỉnh sửa tài nguyên không thuộc sở hữu.

Với Sharing/Permission, nhóm kiểm thử tạo yêu cầu chia sẻ, duyệt/từ chối yêu cầu và đối chiếu thay đổi trên bảng quyền. Sau thao tác approve, danh sách permission phải xuất hiện bản ghi quyền mới; sau thao tác reject, không được phát sinh quyền truy cập ngoài dự kiến. Nhóm Admin được kiểm thử riêng bằng token admin để xác nhận endpoint quản trị chỉ cho phép vai trò phù hợp.

Ngoài luồng nghiệp vụ chính, nhóm triển khai bộ negative tests bắt buộc cho 401, 403, 404, 409 và 400. Các trường hợp điển hình gồm thiếu token, token sai/hết hạn, truy cập trái quyền, id không tồn tại, trùng email và payload thiếu trường bắt buộc. Các test script Postman được dùng để assert status code, assert field response và lưu động các id/token cho request kế tiếp.

Kết quả kiểm thử được tổng hợp theo bảng endpoint, method, test case, expected status, actual status, pass/fail và ghi chú lỗi. Cách tổ chức này giúp truy vết lỗi nhanh, giảm rủi ro hồi quy và bảo đảm hệ thống sẵn sàng cho giai đoạn demo trên môi trường AWS.


## 2.9. HOÀN THÀNH VÀ DEMO DỰ ÁN

Sau khi hoàn thành chức năng backend, hệ thống được đưa lên môi trường triển khai thật trên AWS để kiểm thử tích hợp và trình diễn sản phẩm. Mô hình triển khai gồm frontend tĩnh trên S3, backend Spring Boot chạy trên EC2 và cơ sở dữ liệu PostgreSQL chạy trên RDS.


### 2.9.1 Triển khai ứng dụng lên AWS

#### EC2 AWS

Backend Spring Boot được build thành file jar và triển khai trên một instance EC2. Trên máy EC2, nhóm cài đặt Java runtime, cấu hình security group để mở cổng SSH và cổng dịch vụ backend, sau đó chạy ứng dụng bằng lệnh java -jar. Trong môi trường thực tế, backend có thể được cấu hình chạy kèm systemd hoặc reverse proxy Nginx để tăng độ ổn định và tiện quản lý.

Mục tiêu của bước này là làm cho API backend có thể truy cập từ bên ngoài, đồng thời bảo đảm ứng dụng có thể khởi động lại ổn định sau khi reboot máy chủ.

#### RDS (Relational Database Service)

Cơ sở dữ liệu PostgreSQL được triển khai trên Amazon RDS để tăng độ ổn định và giảm công sức vận hành so với cài đặt thủ công trên máy chủ riêng. Backend cập nhật thông số kết nối như URL, username và password để trỏ sang instance RDS. Sau khi kết nối thành công, nhóm chạy migration để tạo schema và kiểm thử các thao tác CRUD trên dữ liệu thật.

Việc dùng RDS giúp hệ thống có khả năng sao lưu, snapshot và mở rộng tốt hơn, đồng thời tách biệt rõ tầng ứng dụng và tầng dữ liệu.

#### Amazon S3 (Simple Storage System)

Frontend của hệ thống được build và triển khai dưới dạng static website trên Amazon S3. Sau khi build, thư mục dist được upload lên bucket. Nếu cần, nhóm có thể kết hợp CloudFront để tăng tốc độ phân phối nội dung. Ở phía frontend, biến môi trường được cấu hình để gọi đúng API backend thật thay vì localhost.

S3 phù hợp với SPA tĩnh như React/Vite vì dễ triển khai, dễ mở rộng và chi phí vận hành thấp. Trong báo cáo, phần này cần nhấn mạnh rằng frontend production phải trỏ đúng domain backend, đồng thời không còn hard-code môi trường local.

Rủi ro thường gặp khi triển khai AWS gồm lỗi CORS, sai cấu hình security group, sai biến môi trường build và lỗi kết nối mạng giữa EC2 với RDS. Nhóm giảm thiểu các rủi ro này bằng checklist trước và sau triển khai, cùng với smoke test sau mỗi lần release.


### 2.9.2 Demo sản phẩm

Phần demo được thiết kế theo luồng nghiệp vụ thực tế để chứng minh hệ thống hoạt động trọn vẹn từ đầu đến cuối. Nếu báo cáo in ra giấy, phần demo nên trình bày bằng ảnh chụp màn hình theo từng bước và kèm theo đường dẫn hoặc mã QR đến video demo đầy đủ.

Kịch bản demo gồm các bước chính sau:
1. Giới thiệu kiến trúc triển khai trên AWS với frontend, backend và database tách biệt.
2. Thực hiện đăng ký hoặc đăng nhập để lấy token và vào dashboard.
3. Tạo thư mục, upload tài liệu và kiểm tra danh sách tài liệu hiển thị đúng.
4. Xem chi tiết tài liệu, đổi tên hoặc di chuyển tài liệu sang thư mục khác.
5. Gửi yêu cầu chia sẻ từ người dùng A sang người dùng B.
6. Duyệt yêu cầu chia sẻ và kiểm tra quyền truy cập được cập nhật.
7. Thực hiện một thao tác không đủ quyền để hệ thống trả về lỗi 403.
8. Kiểm tra chức năng Admin như xem danh sách user và cập nhật vai trò.

Để buổi demo rõ ràng và thuyết phục, nhóm chuẩn bị sẵn dữ liệu mẫu, log backend, ảnh Postman, và các màn hình đã hoạt động trên môi trường AWS. Cách trình bày này giúp người xem dễ đối chiếu giữa phần mô tả trong báo cáo và hành vi thực tế của hệ thống.

Đoạn kết luận mẫu cho báo cáo:
"Sau khi hoàn tất phát triển với Spring Boot, hệ thống đã được triển khai thực tế trên AWS theo mô hình EC2 - RDS - S3 và kiểm thử đầy đủ các luồng nghiệp vụ chính. Kết quả demo cho thấy ứng dụng đáp ứng tốt các yêu cầu chức năng, phân quyền truy cập và khả năng vận hành ổn định trong phạm vi MVP."
